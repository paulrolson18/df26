Exercise 6: Review Key Elements of Storefront Next

Scenario

Now that your MarketStreet storefront is set up, take some time to understand how the project is structured. Knowing where things live and why will save you time when the product team starts requesting customizations.

Goal

Familiarize yourself with the Storefront Next directory structure and key configuration files.

Task 1: Explore the Directory Structure

Open Visual Studio Code and navigate your Storefront Next project. Use the reference table below to answer these questions:

🔍 Q1: Which file serves as the main application shell and defines the base HTML document layout (<html>, <head>, <body>)?

Storefront Next Directory & File Reference

Directory / FileDescription
src/Core application source code
src/root.tsxThe App Entry Point. Defines the HTML document structure, global layouts, route loaders, and registers middleware chains.
src/routes.tsConfigures routing behavior. Uses flatRoutes() to automatically map files in src/routes/ to URLs.
src/routes/Contains page components mapping to URL paths. Uses React Router 7's file-based routing conventions.
src/routes/action.*.tsxDedicated server actions (e.g., action.cart-item-add.tsx) used for data mutations rather than navigable pages.
src/components/Reusable UI components organized by feature areas (e.g., header/, cart/, product-tile/).
src/components/ui/Contains shadcn/ui components — accessible, fully-customizable base primitives (buttons, inputs, dialogs).
src/lib/Contains logic independent of React: pure utility functions and Commerce API clients (src/lib/api/).
src/hooks/Custom stateful React hooks for accessing client-side data and shared operations (e.g., use-product.ts, use-cart.ts).
src/providers/React Context providers (e.g., cart-provider.tsx) that wrap the root app layout to avoid prop drilling.
src/middlewares/Request/response handlers (e.g., auth-middleware.server.ts) that run before route loaders execute.
src/locales/JSON-based translation files for internationalization.
src/app.cssGlobal stylesheet utilizing Tailwind CSS for UI styling.
config.server.tsCentral configuration for Commerce API connections, site IDs, proxy setups, and storefront settings.
vite.config.tsCore build configuration defining plugins, path aliases, and SSR options.
react-router.config.tsFramework configuration for React Router build options.
package.jsonProject dependencies, metadata, and build/dev npm scripts.

Task 2: Review the package.json File

  1. 1Open package.json in VS Code.
  2. 2Locate the dependencies block. What version of React Router is this project using?
  3. 3What is the project name under the "name" property?
  4. 4Look at the "scripts" block. What command starts the local development server?

Task 3: Review the Config File

Storefront Next centralizes settings in one type-safe file, config.server.ts, at the project root. It has three sections:

  1. 1. Metadata
  2. 2. Runtime (server-only)
  3. 3. App (server and client — commerce, site, and feature settings)

These values can be overridden via .env using PUBLIC__-prefixed variables (e.g., PUBLIC__app__commerce__api__clientId).

  1. 1Open config.server.ts. Under app.commerce.sites, how many sites are configured? What are their defaultLocale and defaultCurrency values?

Exercise 9: AI-Assisted Development Walkthrough

Scenario

Market Street's development team is always looking for ways to ship faster without sacrificing quality. In this session, you'll see how the Agentic B2C Developer Toolkit can accelerate common storefront tasks, from extending product data models to surfacing custom attributes on the product detail page.

Goal

Use the AI developer toolkit to extend the MarketStreet product system object with bag-specific attributes and display them on the PDP.

Task 1: Project Setup — dw.json Configuration

Create a dw.json file in the root of your project. This file configures the B2C CLI to connect to your sandbox.

The fastest, least error-prone way is to let the CLI walk you through it interactively — it prompts for each field and writes the file for you, so there's no risk of a typo'd key name:

b2c setup instance create sandbox

Answer the prompts using the values from your downloaded .env and credentials .csv from Exercise 4. If you're using Claude Code or Agentforce Vibes, you can instead just ask your AI tool to run this command and fill in the values from those downloaded files for you.

If you'd rather see (or hand-edit) the resulting file directly, here's the same configuration as raw JSON:

{
  "hostname": "{YourInstanceWithoutProtocolOrPath}",
  "username": "{YourAccountManagerLogin}",
  "password": "{YourWebDavUxStudioKey}",
  "code-version": "{YourCodeVersionToTarget}",
  "tenant-id": "{yourTenantId}",
  "short-code": "{YourShortCode}",
  "client-id": "{clientID}",
  "client-secret": "{clientSecret}"
}
⚠️ Field names are exact — no camelCase. dw.json keys are all kebab-case: code-version (not version), short-code (not shortCode). A misnamed key isn't validated or rejected — it's silently ignored, so a typo here shows up later as a confusing auth failure during cartridge:deploy, not as an obvious config error.
FieldWhere to Find It
hostnameYour sandbox URL (without protocol). E.g., zzpe-001.dx.commercecloud.salesforce.com
usernameBM → profile icon → Login
passwordWebDAV Access Key (BM → profile → Manage Access Keys → Generate)
code-versionBM → Administration → Site Development → Code Deployment → Active version
tenant-idCombination of realm ID + underscore + sandbox ID (e.g., zzpe_001)
short-codeBM → Administration → Salesforce Commerce API settings
client-id / client-secretFrom Account Manager credentials .csv file

Verify the file is being read correctly before moving on:

b2c setup inspect

This prints the resolved connection with secrets masked — a fast way to catch a typo'd field name before it causes a confusing failure later.

Exercise 11: "Promo Callout" — Wiring a Custom Component into Page Designer

Scenario

Market Street's merchandising team wants to display promotional callouts on storefront pages — managed entirely through Business Manager, with no developer tickets needed for content changes. You'll build a Promo Callout component, wire it into Page Designer, and observe the full round-trip from code to authored content.

Goal

Build and deploy a Page Designer component using Storefront Next's decorator pattern, author content in Business Manager, and understand how the <Region> fallback/authored handoff works.

🎯 Learning Objectives:
•How @Component / @AttributeDefinition / @RegionDefinition decorators turn React code into an authorable Page Designer component
•How cartridge:generate + cartridge:deploy publishes that contract to Business Manager
•How the <Region errorElement={fallback}> pattern hands control between code-owned fallback and author-owned live content
•Why a component can be syntactically perfect and still never render — because a region with live authored content skips its fallback entirely
📋 Prerequisites:
✓Local dev server running (pnpm dev)
✓Business Manager access with Page Designer permissions on the working instance
✓Cartridge already deployed at least once (pnpm cartridge:deploy) so BM recognizes the app cartridge

Step 1: Scaffold the Component with an Authorable Schema

Create src/components/promo-callout/index.tsx:

import { Component } from '@/lib/decorators/component';
import { AttributeDefinition } from '@/lib/decorators/attribute-definition';

@Component('promoCallout', { name: 'Promo Callout', group: 'Content' })
export class PromoCalloutMetadata {
    @AttributeDefinition({ name: 'Message', type: 'string' })
    message!: string;

    @AttributeDefinition({
        name: 'Style',
        type: 'enum',
        values: ['default', 'accent'],
        defaultValue: 'default',
    })
    variant?: 'default' | 'accent';
}

interface PromoCalloutProps {
    message: string;
    variant?: 'default' | 'accent';
}

export default function PromoCallout({ message, variant = 'default' }: PromoCalloutProps) {
    if (!message) return null;
    return (
        <div
            className={
                variant === 'accent'
                    ? 'bg-primary text-primary-foreground px-6 py-4 text-center font-medium'
                    : 'bg-muted text-foreground px-6 py-4 text-center font-medium'
            }>
            {message}
        </div>
    );
}

export function PromoCalloutFallback() {
    return <div className="h-14 bg-muted animate-pulse" />;
}
export { PromoCalloutFallback as fallback };
🔍 Key Concept: The values array in the @AttributeDefinition for variant becomes a dropdown in the BM authoring UI, not free text. This is your first "control surface" — decorators define what merchants can configure.

import { PageType } from '@/lib/decorators/page-type';
import { RegionDefinition } from '@/lib/decorators/region-definition';
import { Region } from '@/components/region';
import { fetchPageWithComponentData } from '@/lib/page-designer/page-loader.server';
import type { Route } from './+types/_app.custom-page';
import CustomBanner from '@/components/custom-banner';

@PageType({
    name: 'Custom Collection Page',
    description: 'Demo page for Page Designer orchestration exercise'
})
@RegionDefinition([{
    id: 'promoZone',
    name: 'Promo Zone',
    description: 'Promotional callout area',
    maxComponents: 1
}])
export class CustomPageMetadata {}

export async function loader(args: Route.LoaderArgs) {
    return { page: await fetchPageWithComponentData(args, { pageId: 'custompage' }) };
}

export default function CustomPage({ loaderData }: Route.ComponentProps) {
    return (
        <>
            <CustomBanner title="Welcome to the Custom Collection!" />
            <Region
                page={loaderData.page}
                regionId="promoZone"
                errorElement={
                    <CustomBanner
                        title="Static fallback — no author content yet"
                        className="bg-muted text-foreground"
                    />
                }
            />
        </>
    );
}
🔍 Key Concept: This is the crux of the exercise. errorElement is what renders until someone authors real content in Business Manager — same code, two very different outputs depending purely on BM state.

Step 3: Generate and Deploy Cartridge Metadata

  1. 1Generate the cartridge metadata from your decorators:
pnpm cartridge:generate
  1. 2Deploy it to your sandbox so Business Manager recognizes the new component:
pnpm cartridge:deploy -r
⚠️ Don't skip the -r flag. cartridge:deploy uploads your cartridge to a code version but does not activate it by default. Business Manager keeps reading page-type and component metadata from whichever code version is currently active — so without -r / --reload (reload/re-activate the code version after deploy), your new "Custom Collection Page" layout and "Promo Callout" component silently won't appear in BM's "Create New Page" picker, even though the deploy itself reported success.
  1. 3Open the generated JSON at cartridges/app_storefrontnext_base/cartridge/experience/components/Content/promoCallout.json and read it side-by-side with your decorator code — this is the "compiled contract" Business Manager will consume.
💡 Tip: Notice how the Message and Style attribute definitions appear as schema fields in the JSON. Your decorators → this JSON → the Business Manager authoring form. No hand-written JSON needed.

Step 4: Author Content in Business Manager

  1. 1In Business Manager, go to Merchant Tools → Online Marketing → Page Designer.
  2. 2Create (or open) a page with ID custompage. Add the region if prompted.
  3. 3Drag the new Promo Callout component into the Promo Zone region.
  4. 4Set Message to something visibly distinct, e.g. 🎉 20% off — authored in Page Designer!
  5. 5Set Style to accent.
  6. 6Assign the page to the appropriate aspect if required, then Publish.
⚠️ The page must be Published, not left as Draft. If you reload the storefront and the region still doesn't show authored content — or the whole route errors instead of falling back — check the page's status in Page Designer. A Draft-only page isn't served by the Shopper Experience API at all, which produces a very different failure than "empty region": the API request for the page itself returns a 404, and neither branch of your <Region> renders as expected.

Step 6: Discussion — The "Invisible Component" Gotcha

Case study: Imagine a developer builds a TrustBadge component, registers it correctly, deploys it, and places it as the errorElement of a region on the About Us page. The code is syntactically perfect. The cartridge JSON is correct. But the badge never renders.

Why? The region already had live authored content from a merchandiser. Regions with authored content skip their fallback entirely — the errorElement branch is permanently dead code for that region.

💬 Discussion Questions:

"If a component you build never shows up, what's the first thing to check — the code, or the region's current authored state?"

"What's the risk of assuming errorElement content is what production visitors will always see?"
